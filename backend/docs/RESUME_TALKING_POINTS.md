# 项目讲解要点

## 项目定位

在保留旧单体作为行为参考和回退路径的前提下，新建独立微服务工程。系统按身份、学习和 AI 三个限界上下文拆分，网关统一承担 JWT 鉴权、身份头清洗、限流和跨域控制。

## 可以写入简历的量化成果

- 面向 20,000 条错题数据优化复习列表查询，为 `user_id`、`question_status`、`update_time DESC` 建立联合索引。经 Gateway 端到端压测，p95 从 1980 毫秒降至 767 毫秒，吞吐从 16.74 提升至 40.56 请求每秒，连续三轮均无失败请求。

该数据来自固定本地 Docker 环境、100 次预热、1,000 次正式请求、20 并发的前后对比中位数。详见 `docs/BENCHMARKING.md`，面试时应明确其为本地基准，不外推为生产容量。

## 可深入说明的工程设计

- 按数据所有权和聚合一致性拆分服务，错题、错因、笔记和复习仍处于同一个 Learning 边界，避免为拆分而拆分。
- AI 服务不能跨库查询 Learning 数据。生成题和 OCR 入库通过版本化内部契约调用，避免隐式数据库耦合。
- RabbitMQ 消费端以 `eventId` 实现幂等，失败经过有限重试后进入死信队列。发布端使用 Confirm、有限重试和失败指标，但不把它误说成事务消息。
- MySQL 使用 GTID 主从复制和读写路由。由 RabbitMQ 事件构建的 AI 分析读模型走从库，事务以及错题、知识点、概览等写后读查询固定走主库；副本连接不可用时回退主库。
- RAG 文档以 SHA-256 校验值幂等导入，服务重启不会清空向量表。
- SkyWalking 自动采集 Gateway、Feign、RabbitMQ、JDBC 和 Redis 调用链，BanyanDB 持久化链路数据，日志通过 traceId 与调用链关联。

## 需要如实说明的取舍

- 当前为一主一从且没有仲裁、VIP 和 fencing，不实现自动故障转移，避免发生双主写入。生产环境可替换为云数据库高可用方案或 MGR。
- 当前不使用 Outbox。数据库提交成功但消息最终发布失败仍存在极小窗口，Confirm、重试和指标只能降低风险。若关键事件需要更强可靠性，应引入 Outbox 和 CDC。
