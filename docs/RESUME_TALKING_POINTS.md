# 简历讲解要点

## 30 秒版本

在不影响原 DDD 单体的前提下，新建并行微服务工程，按身份、学习和 AI 三个限界上下文拆分。网关统一 JWT 和限流，服务间用 Feign 和内部令牌同步协作，用 RabbitMQ 传递登录与学习事件；数据库按服务拆分，并实现 MySQL GTID 主从读写路由和从库故障回退。

## 可深入说明的设计

- 没有按 Controller 数量拆服务，而是按数据所有权和聚合一致性拆分，错题、错因、笔记、复习仍在同一个 learning 边界中。
- AI 不能跨库查错题，生成题和 OCR 入库都通过版本化内部契约，减少隐式耦合。
- 消费端使用 `eventId` 唯一键和本地事务处理 RabbitMQ 重复投递；失败重试后进入 DLQ。
- 发布端有 Confirm、有限重试和失败指标，但主动说明没有 Outbox 时仍存在提交后丢消息窗口。
- 异步主从可能读到旧数据，因此事务、鉴权、写后读走主库；只有明确的只读查询走从库。
- PgVector 文档导入按 SHA-256 幂等，不再在每次启动清空向量表。
- SkyWalking Agent 自动采集 Gateway、Feign、RabbitMQ、JDBC、Redis 调用链，OAP 使用 BanyanDB 持久化，UI 展示服务拓扑、慢请求和错误链路；日志通过 `traceId` 与 Trace 关联。

## 取舍题

为什么不自动故障转移：当前只有一主一从，没有仲裁、VIP 和 fencing，自动提升可能造成双主。演示版本提供延迟检查和手动提升，生产可引入 Orchestrator、MGR 或云数据库 HA。

为什么没有 Outbox：项目选择直接发布以控制复杂度，并用 Confirm、重试、指标降低风险；如果登录画像或学习分析成为强可靠业务，会优先补 Outbox + CDC。

为什么保留旧单体：并行目录让接口行为可对照、回退简单，也适合 Strangler Fig 渐进迁移，而不是一次性替换全部流量。
